## 1️⃣ Understanding the ECS Hierarchy 🏗️

```
📦 CLUSTER
   └── 🔧 SERVICE (a group of tasks — ensures desired count stays running)
        └── 📋 TASK (a group of containers — usually just 1)
             └── 🐳 CONTAINER (the actual running container)
```

| Term | Definition |
|---|---|
| 🖥️ **Cluster** | The hardware (a set of nodes) your applications run on |
| 🐳 **Container** | The final running instance of a microservice's Docker image |
| 📋 **Task** | A group of one or more containers (usually just one) |
| 🔧 **Service** | A group of tasks — ensures a *desired number* of task instances always stays running |

> 💡 **Example:** Want 10 instances of a microservice? Define it as a **service** with a desired count of 10 — the service guarantees that count stays running.

## ❓ Extra Important Question: "Why would I ever put multiple containers in the same task instead of just running separate tasks?"

> 💡 **Answer:** This is the classic **"sidecar" pattern**. You'd group containers in one task when they need to be tightly coupled — scheduled together, sharing the same network namespace and storage volumes, and living/dying as a unit. Common examples: a logging or monitoring agent that needs to sit right next to your main application container, or a proxy container that handles TLS termination for your app container. If containers don't need that tight coupling, keeping them as separate tasks (and possibly separate services) gives you more independent scaling and deployment flexibility — which is usually the better default.
