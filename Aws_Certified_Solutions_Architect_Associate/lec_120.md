# 🎯 Lecture 120: Why Can't We Reach Our Instances? (A VPC Mystery 🕵️)

> 📚 **Course:** AWS Certified Solutions Architect – Associate
> 🧩 **Section:** Virtual Private Cloud (VPC)
> ⏱️ **Type:** Hands-On Demo + Troubleshooting (⭐ Continues directly from Lecture 119!)

## 🎯 What This Lecture Is About

> 🎬 We built a VPC with two subnets and two EC2 instances, both with public IPs. Now let's try to reach them. Spoiler: **it won't work**, and understanding why is the key lesson.

```
1️⃣ Inspect the Running Instances
2️⃣ Try to Ping the Instance
3️⃣ Fix the Security Group (and Try Again)
4️⃣ Try EC2 Instance Connect
5️⃣ The Real Reason It Fails
```

---

## 1️⃣ Inspect the Running Instances 🔍

Both instances are now **running**, and each has **two** IP addresses:

| Instance | Subnet | Private IP starts with | Public IP |
|---|---|---|---|
| 🌍 `Public-EC2-Instance` | `my-public-subnet` | `69.208.1.x` | ✅ Assigned |
| 🔒 `Private-EC2-Instance` | `my-private-subnet` | `69.208.0.x` | ✅ Assigned |

> 🎯 **Key Insight:** The private IP always matches the subnet's CIDR block. Only the **last 8 bits** change from one instance to the next, so `69.208.1.x` = public subnet and `69.208.0.x` = private subnet. Just by looking at the IP, you can tell which subnet an instance is in.

---

## 2️⃣ Try to Ping the Instance 🏓

We copied the public IP and ran `ping` from a terminal.

```
❌ Result: Request timed out
```

> 🧒 **What is "ping"?** It's like knocking on a door to ask "Are you there?" If someone answers, the server is reachable. If you get silence (a timeout), something is blocking the knock.

### 🕵️ First Suspect: The Security Group

> 💡 **Rule of thumb:** When you see a timeout, **check the security group first.**

The security group only allowed **TCP traffic** (like SSH). Ping uses a different protocol called **ICMP**, which wasn't allowed.

---

## 3️⃣ Fix the Security Group (and Try Again) 🔧

```
1️⃣ Go to ec2-security-group → Edit inbound rules
2️⃣ Add rule: "All ICMP - IPv4"
3️⃣ Source: Anywhere
4️⃣ Save
```

> 🧒 **In simple words:** We told the security guard at the gate, "Please let ping requests in." Now the guard allows both TCP and ICMP traffic.

```
❌ Result: Ping STILL doesn't work!
```

---

## 4️⃣ Try EC2 Instance Connect 💻

We tried the browser-based **EC2 Instance Connect** (SSH) on the instance.

```
❌ Result: Waits a long time, then fails
```

### 📊 So Far

| Test | Security Group Allows It? | Does It Work? |
|---|---|---|
| 🏓 Ping | ✅ Yes (we added ICMP) | ❌ No |
| 🔑 SSH / Instance Connect | ✅ Yes (TCP port 22) | ❌ No |

> 🤔 The security group is fine, yet nothing works. So the problem must be **somewhere else**.

---

## 5️⃣ The Real Reason It Fails 💡

> 🎯 **The Answer:** When you create a **new VPC** and **new subnets**, AWS does **not** automatically connect them to the internet. By default, all new subnets are effectively **private**, meaning:

```
🚫 Traffic from the internet CANNOT get into the subnet
🚫 Instances in the subnet CANNOT reach the internet
```

### 🧒 In Simple Words: The Colony Analogy 🏘️

> Imagine a gated colony (the VPC) with two streets (the subnets). **There is no main gate or road connecting the colony to the outside world yet.**
>
> - 🔐 The **security group** is the **guard at each house's door**. They decide who can enter that house.
> - 🚪 The **subnet's connection to the internet** is the **colony's main gate and road**.
>
> The guard at the door is useless if visitors can't even reach the colony. You can give instructions to the guard all day, but with no road, nobody arrives.

### 📌 The Big Lesson

```
🔐 Security Group = controls traffic that has ALREADY reached the instance
🚪 Subnet internet connection = decides whether traffic can reach the subnet AT ALL

Without the subnet connection, security groups don't matter.
```

> 🎯 **Exam Tip:** A **public IP address alone** doesn't make an instance reachable. The subnet needs a **path to the internet**. We'll learn how to build that path in the next lecture!

---

## ❓ Extra Important Question: "If I'm troubleshooting an EC2 instance I can't reach, what's the correct order to check things?"

> 💡 **Answer:** Work from the **outside in**, checking each layer the traffic must pass through:
>
> 1. **Does the instance have a public IP?** (If it needs to be reachable from the internet.)
> 2. **Does the subnet have a route to the internet?** (Route table and internet gateway. This was the missing piece in our demo.)
> 3. **Does the Network ACL allow the traffic?** (The subnet-level firewall, covered later.)
> 4. **Does the security group allow the traffic?** (The instance-level firewall.)
> 5. **Is the instance itself healthy?** (Is the service running? Is the OS firewall blocking it?)
>
> In our demo, we jumped to step 4 because "timeout = security group" is a common first guess. But the real problem was at step 2. A good habit: when the obvious check doesn't fix it, **zoom out** and check the network path, not just the instance.

---

## 📋 Master Summary Table

| Layer | What It Controls | Status in Our Demo |
|---|---|---|
| 🌍 **Public IP** | Gives the instance an internet-facing address | ✅ Assigned |
| 🚪 **Subnet route to internet** | Lets traffic enter/leave the subnet | ❌ **Missing!** |
| 🔐 **Security Group** | Filters traffic reaching the instance | ✅ Configured correctly |

## ✅ Final Takeaways

```
🏓 Ping uses ICMP; SSH uses TCP. The security group must allow the right one
⏱️ A "timeout" usually means traffic is being blocked somewhere along the way
🚪 New VPC + new subnets = NO internet access by default
🔐 Security groups only work on traffic that has already reached the subnet
🌍 A public IP alone does NOT make an instance reachable
🎯 To make a subnet truly "public," it needs a path to the internet (coming next!)
```
