## 1️⃣ Concept Questions 🧠

| ❓ Question | ✅ Answer | 💡 Why |
|---|---|---|
| What's a **good availability** target? | **99.99%** (four nines) | Allows about **4.5 minutes** of downtime a month |
| What about **99.999%** (five nines)? | Very hard to achieve | Only about **26 seconds** of downtime a month |
| What's a **good durability** target? | **11 nines** (99.999999999%) | Once data is lost, **it's gone forever**. You don't want your bank to lose your account data |
| What does **consistency** measure? | Do you get the **most recent data, whichever copy** you query? | With multiple copies, the question is: **is the data the same across all copies?** |
| What is **eventual consistency**? | A **small lag** (a few seconds) before updates reach all replicas | The replica stores the change, then slowly passes it on. For a few seconds, different replicas may return **different values** |

## 2️⃣ "Which Pillar Is This?" Scenarios 🔍

| 🗣️ What the User Says | 🏛️ Pillar | 💡 Why |
|---|---|---|
| "I **can't access** the website right now." | 🚪 **Availability** | A temporary access problem |
| "My uploaded photo **disappeared permanently**." | 🗄️ **Durability** | **Permanent data loss** |
| "I updated my profile, but my friend **still sees the old one** after a few seconds." | 🔄 **Consistency** (specifically **eventual consistency**) | Different copies hold different values for a short time. Typical for social media apps |
| "I need to handle **10 more users** next week." | 📈 **Scalability** | Handling more users and data |
| "I need the **exact stock price immediately** after the update." | 🔄 **Consistency** (needs **strong consistency**) | In finance, every user must see the **same data all the time** |

> 📝 *Note: The lecture mentions that a friend might see an old profile after "a few minutes or hours." In practice, eventual consistency usually catches up within **seconds**. Long delays would point to a different kind of problem.*

---

## 3️⃣ "Strong or Eventual?" Scenarios ⚖️

| 🏢 Use Case | 🏛️ Model | 💡 Reasoning |
|---|---|---|
| 💹 **Financial trading application** | 🔒 **Strong consistency** | Exact, up-to-the-second correctness is essential |
| ❤️ **Social media likes count** | ⏳ **Eventual consistency** | A few seconds of delay is fine. **Showing the page quickly** matters more than an up-to-the-second count |

## 4️⃣ The Big Picture 🖼️

> 💡 **What We Covered in This Section:** All four pillars, specifically from the perspective of **databases and systems that store data**.

```
✅ Every application wants HIGH availability
✅ Every application wants HIGH durability
✅ Every application wants HIGH scalability
✅ Every application wants HIGH consistency
```

### ⚠️ But There's a Trade-Off!

> 🎯 **High consistency has a performance cost.** (Strong consistency means slower writes.) So you must **choose the right consistency model** for each application's needs.

> 🧒 **In simple words:** You can't always have everything at maximum. Good architects **balance** the pillars based on what the business really needs. This matches the "architect mindset" we saw in Lecture 87.

---

## ❓ Extra Important Question: "If I improve availability by adding more copies, which other pillars does that affect?"

> 💡 **Answer:** Adding copies has **ripple effects** across the pillars. This is a great way to test your understanding:
>
> | Pillar | Effect of Adding More Copies |
> |---|---|
> | 🚪 **Availability** | ✅ **Improves**: if one copy is down, others serve users |
> | 🗄️ **Durability** | ✅ **Improves**: if one copy is lost, others remain |
> | 📈 **Scalability** | ✅ **Improves reads** (many copies can serve readers), but ❌ **doesn't help writes** with simple read replicas |
> | 🔄 **Consistency** | ⚠️ **Gets harder**: copies must stay in sync, which costs time |
>
> So one design choice (add copies) pushes **three pillars up and one pillar to be managed**. This is why the course spent time on all four together instead of one at a time.

## 📋 Master Cheat Sheet

```
🚪 AVAILABILITY → can I access it? → target ≈ 99.99% (≈4.5 min/month) | 99.999% ≈ 26 sec/month
🗄️ DURABILITY   → will it still exist? → target = 11 nines
📈 SCALABILITY  → can it handle more? → vertical (bigger) or horizontal (more servers)
🔄 CONSISTENCY  → same data everywhere?
     🔒 Strong   → always latest, slower  → banking, trading, inventory
     ⏳ Eventual → catches up in seconds, faster → social feeds, likes, reviews, profiles
⚖️ High consistency costs performance → pick the model your application needs
```
