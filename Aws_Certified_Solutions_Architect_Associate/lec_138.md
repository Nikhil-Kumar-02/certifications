## 🎯 What This Lecture Is About

> 🎬 Horizontal scaling means **adding more servers**. But *how*, exactly? Here are two simple approaches:

```
1️⃣ Read Replicas
2️⃣ Distributed Data Stores
```

---

## 1️⃣ Read Replicas 📖

> 💡 **Core Idea:** Create **read-only copies** of your **primary database**. Changes made on the primary are **automatically copied** to the replicas.

```
✍️ Applications that CHANGE data → talk to the PRIMARY database
📖 Applications that only READ data → talk to the READ REPLICAS
```

### 🧒 In Simple Words: The Library 📚

> Imagine one **original book** in a library. Only the **author** (the primary) can edit it. But hundreds of readers want to read it, which causes a queue. So the library makes **photocopies** (read replicas). Readers use the photocopies, and the author's original stays free for writing. When the author edits the original, the photocopies get updated too. ✨

### ✅ Who Uses Which?

| Workload | Connects To |
|---|---|
| 🛒 **Transactional applications** (change data) | **Primary** database |
| 📊 **Reporting and analytics** (just `SELECT` queries) | **Read replica(s)** |

> 💡 You can have **multiple** read replicas.

### 🎯 The Benefit

> The primary can **focus on writes** and transactional work, so it gives **great performance** to its users. Heavy reports no longer slow it down.

### ⚠️ The Limitations

| Limitation | Why |
|---|---|
| ✍️ **Doesn't solve write bottlenecks** | Say your primary handles writes for **10,000 users** and you want **30,000** users all modifying data. Replicas are read-only, so **all writes still go to the one primary** |
| 📦 **Doesn't increase storage capacity** | A replica holds an **exact copy** of the primary's data. Two copies of the same data don't let you store **more** data |

> 🎯 **Exam Tip:** **Read replicas fix READ bottlenecks only.** Not write bottlenecks. Not storage size.

---

## 2️⃣ Distributed Data Stores 🌐

> 💡 **Core Idea:** A **distributed database** spreads your data across **many servers**, with something **coordinating** between them. It automatically **splits both the data and the queries** across all the servers.

```
🖥️ Server 1: part of the data
🖥️ Server 2: part of the data
🖥️ Server 3: part of the data
...and queries are run across them in parallel
```

> 📝 *Bonus term: Splitting data across servers like this is often called **sharding**. (Not used in the lecture, but you'll see it everywhere.)*

### 🧒 In Simple Words: The Encyclopedia 📚

> Instead of **one giant book** held by one librarian, split the encyclopedia into **many volumes** across **many shelves** (even many libraries). Each librarian handles their own volume, and a coordinator knows which volume has what. You can keep adding shelves as the encyclopedia grows.

### ✅ Advantages

| Advantage | Detail |
|---|---|
| ♾️ **Practically unlimited capacity** | Keep **adding servers** as data grows |
| 🛡️ **High availability** | Servers can be spread across **multiple zones and regions**. If one goes down, others serve users |

### ❓ The Big Question It Raises

> With multiple copies of data on different servers, **how do you make sure all servers have the same data while still performing well?** That's the **consistency** pillar, our next lecture.

---

## ⚖️ Read Replica vs Distributed Data Store

| Feature | 📖 Read Replica | 🌐 Distributed Data Store |
|---|---|---|
| 🔧 **What it is** | **Read-only copy** of the primary | Data **split across many servers** |
| 📖 **Scales reads?** | ✅ Yes | ✅ Yes |
| ✍️ **Scales writes?** | ❌ No (still one primary) | ✅ Yes |
| 📦 **Scales storage?** | ❌ No (same data, copied) | ✅ Yes (unlimited, add servers) |
| 🧩 **Complexity** | ✅ Simple | ❌ More complex |
| 🎯 **Best for** | Heavy **reporting and analytics** on top of a transactional database | **Very large** data and heavy read/write workloads |

## ❓ Extra Important Question: "Is a read replica the same thing as a standby database?"

> 💡 **Answer:** **No**, and this mix-up is common. (In the lecture, the instructor accidentally says "standby" while talking about read replicas.)
>
> | | 📖 Read Replica | 🛡️ Standby Database |
> |---|---|---|
> | **Purpose** | **Scale reads** (performance) | **Failover** (availability) |
> | **Used for queries?** | ✅ Yes, serves read traffic | Usually ❌ No, it just waits as a backup *(in the classic RDS Multi-AZ setup)* |
> | **Takes over if the primary fails?** | Not automatically in the classic setup | ✅ Yes, that's its whole job |
>
> 🧒 **In simple words:** A read replica is an **extra cashier** who helps serve customers. A standby is a **spare manager** sitting in the back office, who steps in only if the main manager is absent.
>
> We'll meet both when we get to **Amazon RDS**. Newer RDS options blur this line a little (some setups give you readable standbys), so check the current docs when you get there.

## 📋 Master Summary Table

| Concept | What It Does | Limitation |
|---|---|---|
| 📖 **Read Replica** | Handles **read** workloads using read-only copies | Can't fix write bottlenecks or storage size |
| 🌐 **Distributed Data Store** | Splits data and queries across **many servers** | More complex, with consistency to manage |

---

## ✅ Final Takeaways

```
📖 Read replica = read-only copy of the primary. Reads go to replicas, writes go to the primary.
✅ Best for reporting and analytics (heavy SELECT queries)
❌ Doesn't help with write bottlenecks or total storage size
🌐 Distributed data store = data + queries split across MANY servers
✅ Practically unlimited capacity + high availability across zones/regions
🔄 Both bring a consistency question: are all the copies the same?
🛡️ Read replica ≠ standby (replica = performance, standby = failover)
```
