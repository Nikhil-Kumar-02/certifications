# 🎯 Lecture 128: Hands-On — Creating a NAT Gateway (and Cleaning Up)

> 📚 **Course:** AWS Certified Solutions Architect – Associate
> 🧩 **Section:** Virtual Private Cloud (VPC)
> ⏱️ **Type:** Hands-On Demo (⭐ Puts Lecture 127's theory into practice!)

---

## 🎯 What This Lecture Is About

> 🎬 Our private instance is cut off from the internet: X-Ray shows traces only from the public instance. Now we'll give the private instance **outbound-only** internet access using a **NAT Gateway**, and then clean everything up.

```
1️⃣ Create the NAT Gateway
2️⃣ Update the Private Route Table
3️⃣ Verify in X-Ray
4️⃣ The Surprise: Whose IP Is That?
5️⃣ Clean Up (In the Right Order!)
```

---

## ⚠️ Cost Warning First

> 💰 A **NAT Gateway costs money** while it exists, and an Elastic IP can also cost money if left unused. **Do the cleanup at the end** so you don't get surprise charges.

---

## 1️⃣ Create the NAT Gateway ☁️

Navigate: **VPC → NAT Gateways → Create NAT gateway**

| Setting | Choice |
|---|---|
| 🌍 **Subnet** | **`my-public-subnet`** (always a *public* subnet!) |
| 📌 **Elastic IP** | Allocate one (the console assigns it automatically) |

### 🤔 Wait, Why Put It in the PUBLIC Subnet?

> 🧒 **In simple words:** The NAT Gateway is the **front desk that posts the mail**. The front desk itself must be able to **reach the outside world**, so it has to sit on the **public street**, where the main gate (Internet Gateway) is reachable. The private street's residents just hand their mail to the front desk.

```
🔒 Private instance → ☁️ NAT Gateway (in public subnet) → 🚪 Internet Gateway → 🌍 Internet
```

> 📌 **Remember:** A NAT Gateway placed in a private subnet **won't work**. It needs the route to the Internet Gateway.

---

## 2️⃣ Update the Private Route Table 🪧

Creating the gateway isn't enough. We must **point traffic to it**.

### 🔍 Which Route Table Does the Private Subnet Use?

```
my-private-subnet → Route table tab → My VPC Route Table
```

### ➕ Add the Route

```
1️⃣ VPC → Route Tables → My VPC Route Table → Edit routes
2️⃣ Add route → Destination: 0.0.0.0/0
3️⃣ Target: NAT Gateway → (select the one you created)
4️⃣ Save routes
```

> 💡 **Nice design bonus:** This route is on the **shared** table that new subnets use by default. So any new private subnet you create later automatically gets **outbound internet access (no inbound)**.

### 📊 The Final Layout

| Route Table | Used By | Internet Route |
|---|---|---|
| 🌍 **My Public Subnet Route Table** | `my-public-subnet` | `0.0.0.0/0` → **Internet Gateway** (two-way) |
| 🔒 **My VPC Route Table** | `my-private-subnet` | `0.0.0.0/0` → **NAT Gateway** (outbound only) |

---

## 3️⃣ Verify in X-Ray 👀

```
Refresh X-Ray traces → wait about 30 seconds
```

```
✅ Traces from the PRIVATE instance start appearing again!
```

> 🎯 **Result:** The private instance can now **call out** to the internet, but we still **can't connect in** to it. That's exactly the goal.

---

## 4️⃣ The Surprise: Whose IP Is That? 🕵️

Compare the **client IPs** in X-Ray:

| Instance | Client IP in X-Ray |
|---|---|
| 🌍 **Public instance** | Its **own public IP** |
| 🔒 **Private instance** | **Not** its own public IP! It's a different address |

### 🔍 Where Does That Mystery IP Come From?

```
Check VPC → NAT Gateways → the Elastic IP of the NAT Gateway
✅ It's a MATCH!
```

> 🧒 **In simple words:** Remember the front desk posting mail under the **company's address**? That's what's happening. The outside world (X-Ray) sees the **NAT Gateway's Elastic IP** as the sender, never the private instance's own address. The private instance stays hidden. 🥷

> 🎯 **Key Insight:** **Outbound requests from private instances appear to come from the NAT device's IP address.**

---

## 5️⃣ Clean Up (In the Right Order!) 🧹

> ⚠️ **Order matters.** Some resources can't be deleted while others still depend on them.

| # | Action | Why This Order |
|---|---|---|
| 1️⃣ | **Delete the route** to the NAT Gateway (My VPC Route Table) | Remove the dependency first |
| 2️⃣ | **Delete the route** to the Internet Gateway (My Public Subnet Route Table) | Same reason |
| 3️⃣ | **Delete the NAT Gateway** (Actions → Delete NAT gateway) | Takes a little while to finish |
| 4️⃣ | **Release the Elastic IP** (Actions → Release Elastic IP addresses) | ❗ Only possible **after** the NAT Gateway is fully deleted. If you get a permission error, wait a bit and retry. |
| 5️⃣ | **Terminate the EC2 instances** | Stops compute charges |
| 6️⃣ | **Detach, then delete the Internet Gateway** (Actions → Detach from VPC → Delete) | A gateway must be detached before deleting |
| 7️⃣ | **Delete the custom VPC** *(optional)* | Removes everything inside it |

### 💡 About Deleting the VPC

> The remaining items (VPC, subnets, route tables) are **just networking configuration and cost nothing**. You can keep the VPC for later reference or practice, or delete it. Deleting the VPC also removes the things inside it.

---

## ❓ Extra Important Question: "Why couldn't I release the Elastic IP right away? It said I don't have permission."

> 💡 **Answer:** The error message is a bit misleading. The real reason is that the Elastic IP is **still in use by the NAT Gateway**. AWS won't let you release an IP address that's attached to a running resource. A NAT Gateway takes a short while to fully delete, so if you try to release the IP too soon, it fails. Once the NAT Gateway shows as **deleted**, the Elastic IP becomes free and the release works. This is also a good **exam fact**: *you cannot release the Elastic IP of a NAT Gateway while the NAT Gateway still exists.*

| 3️⃣ | Check X-Ray | Private instance's calls return |

## ✅ Final Takeaways

```
☁️ NAT Gateway goes in a PUBLIC subnet and needs an ELASTIC IP
🪧 Private route table: 0.0.0.0/0 → NAT Gateway (outbound only!)
🌍 Public route table: 0.0.0.0/0 → Internet Gateway (two-way)
🥷 Outbound traffic from private instances appears to come from the NAT Gateway's IP
🔒 We can call OUT from the private instance, but nobody can call IN
🧹 Cleanup order: routes → NAT Gateway → Elastic IP → EC2 → Internet Gateway → VPC
❗ You can't release the Elastic IP until the NAT Gateway is deleted
```
