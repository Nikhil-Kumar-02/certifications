## 1️⃣ Navigating to VPCs 🧭

```
Services → type "VPC" → "Isolated Cloud Resources" → click through
```

> 🎯 **Key Insight:** VPCs exist **in every region** — and AWS pre-creates a default one for you automatically.

---

## 2️⃣ Exploring the Default VPC 🌐

```
📛 Name: (empty — default VPCs typically have no name)
✅ State: Available
🔢 CIDR: A range of IP addresses assigned to it (covered in more depth later)
```

> 💡 **Why This Matters:** When you're new to AWS and don't want to deal with VPC/subnet complexity yet, you can just **use the default VPC and subnets** to get started quickly.

---

## 3️⃣ Counting Subnets = Counting Availability Zones 🔢

> 🎯 **Key Insight:** The number of default subnets in a region **always matches** the number of Availability Zones in that region.

### 🎓 Example: Asia Pacific (Mumbai) — `ap-south-1`

```
🏢 3 Availability Zones → ap-south-1a, ap-south-1b, ap-south-1c
📦 3 Subnets → one automatically created in EACH availability zone
```

> 💡 Selecting each subnet in the console confirms this — one subnet lands in `1a`, another in `1b`, another in `1c`.

---

## 4️⃣ Comparing Regions: Mumbai vs. N. Virginia 🌍

### 🇮🇳 Asia Pacific (Mumbai) — `ap-south-1`

```
🏢 3 Availability Zones → 📦 3 Subnets
```

### 🇺🇸 US East (N. Virginia) — `us-east-1`

```
🏢 6 Availability Zones (us-east-1a through us-east-1f) → 📦 6 Subnets
```

> 🎯 **Fun Fact:** `us-east-1` is widely considered the **most popular AWS region**, since most new AWS features are released there first.

---

## ❓ Extra Important Question: "Since AWS already gives me a working default VPC and subnets, why would I ever bother creating my own custom VPC?"

> 💡 **Answer:** The default VPC is great for quick experiments and learning, but it makes broad, generic choices that don't fit every real-world need. A custom VPC lets you: control your **own IP address ranges (CIDR blocks)** to avoid conflicts when connecting to other networks (like on-premises data centers via VPN); design your **own mix of public and private subnets** tailored to your actual security requirements; set up **custom routing** (route tables, NAT gateways, VPC peering) for specific architectural needs; and apply **fine-grained security controls** (security groups, NACLs) matched to your application. In short — the default VPC is a reasonable "batteries included" starting point, but production architectures almost always move to custom VPCs for control, security, and scalability reasons.
