## 1️⃣ Lambda Is Stateless 🚫💾

> 💡 **Core Idea:** A Lambda function **cannot store state** between multiple requests/invocations.

### 🎯 Where Should You Store State Instead?

| Service | Type |
|---|---|
| 🗃️ **Amazon S3** | Object storage |
| ⚡ **Amazon DynamoDB** | Serverless NoSQL database |

---

## 2️⃣ Temporary Disk Space (`/tmp`) 📁

```
💾 Available disk space: 500 MB
⚠️ NON-PERSISTENT — wiped after execution completes
```

> 🎯 **Key Insight:** Need to do file operations during execution? You get `/tmp`, but don't rely on it surviving beyond a single invocation.

---

## 3️⃣ Memory Allocation Increments 💾

```
📊 Range: 128 MB → 3 GB (3008 MB)
📈 Increments: 64 MB at a time
```

---

## 4️⃣ Cost & CPU Are Both Tied to Memory 💰⚙️

> 💡 **Core Idea:** As you increase memory:

```
🔼 CPU power increases
🔼 Cost increases
```

Both are **directly proportional** to the memory you allocate.

> ⚠️ **Reputation Check:** Lambda is often considered a relatively **expensive** compute option at scale — worth checking AWS's official pricing page for the full breakdown before committing to a heavy Lambda-based architecture.

---

## 5️⃣ Free Tier 🆓

```
🎁 ~1 million free requests per month
```

> 🎯 **Key Insight:** This generous free tier makes Lambda extremely approachable for learning, prototyping, and even many low-traffic production workloads.

## ❓ Extra Important Question: "Since Lambda is stateless, how do multiple invocations of the SAME function share any data at all — even indirectly?"

> 💡 **Answer:** They don't share data through the function's own memory or disk — each invocation is meant to be treated as isolated. The `/tmp` directory *can* occasionally persist across invocations if AWS happens to reuse the same underlying execution environment ("warm start"), but this is an implementation detail you should **never rely on** — it's not guaranteed and Lambda can spin up a fresh environment at any time. The correct, reliable pattern for sharing data between invocations is always an **external store** — S3 for files/objects, DynamoDB for structured data, or other services like ElastiCache for shared in-memory caching. Treating Lambda as truly stateless from a design perspective avoids subtle bugs that only show up when AWS's internal execution environment reuse behavior changes.

## 📋 Master Cheat Sheet

```
🚫 STATELESS → use S3 or DynamoDB for state between invocations
📁 /tmp → 500 MB, NON-PERSISTENT (wiped after execution)
💾 MEMORY → 128 MB to 3 GB, in 64 MB increments
💰 COST & CPU → both scale UP as memory increases
🆓 FREE TIER → ~1 million requests/month
⏱️ TIMEOUT → default 3s, max 900s (15 min)
🔍 MONITORING → CloudWatch (metrics/logs) + X-Ray (tracing)
```

## ✅ Final Takeaways

```
🚫 Lambda = STATELESS. External storage (S3/DynamoDB) is a MUST for persisting data.
📁 /tmp gives 500 MB, but it's NON-PERSISTENT — don't rely on it surviving.
💾 Memory: 128 MB–3 GB in 64 MB steps → drives BOTH cost and CPU power.
🆓 ~1 million free requests/month makes Lambda very approachable to start with.
⏱️ Max execution time: 900 seconds (15 min) — break longer jobs into multiple invocations.
🔍 CloudWatch (metrics/logs) + X-Ray (tracing) = your Lambda observability toolkit.
```
