## 🎯 What This Lecture Is About

> 🎬 Security groups protect **individual resources** (like one EC2 instance). But what if you want to stop certain traffic from entering the **subnet at all**? That's the job of a **Network Access Control List (NACL)**.

## 1️⃣ What Is a NACL? 🚧

> 💡 **Core Idea:** A NACL is a **stateless firewall at the subnet level**.

| Tool | Where It Protects |
|---|---|
| 💂 **Security Group** | **Individual resources** (an EC2 instance, a database) |
| 🚧 **NACL** | The **whole subnet**, at the entrance |

### 🧒 In Simple Words: Two Layers of Guards 🏘️

> Picture the colony again:
> - 🚧 The **NACL** is the **guard at the street entrance**. He decides who may enter the *street* at all.
> - 💂 The **security group** is the **guard at each house's door**. He decides who may enter *that particular house*.
>
> If the street guard turns you away, **you never even reach the houses**. So a NACL that blocks traffic means that traffic **never reaches your resources**, no matter what the security groups say.

---

## 2️⃣ How NACLs Behave by Default 📋

| Rule | Detail |
|---|---|
| 🔗 **Association** | **Every subnet must be associated with a NACL** |
| ✅ **Default NACL** | Allows **all** inbound and **all** outbound traffic |
| ❌ **Custom (new) NACL** | **Denies all** inbound and outbound traffic until you add rules |

> 📌 **Exam Tip:** Default NACL = **open**. New custom NACL = **closed**. (Compare this with security groups, where a new group denies inbound but allows outbound.)

---

## 3️⃣ How NACL Rules Work 🧮

| Feature | Detail |
|---|---|
| 🔢 **Rule number (priority)** | Every rule has a number. **Lower number = higher priority.** |
| ✅❌ **Allow AND Deny** | NACLs support **both** allow rules and deny rules |
| 🔄 **Inbound and Outbound** | Separate rule lists, and they work the same way |
| 🚫 **Default decision** | If no rule matches, the traffic is **denied** |

### 🧒 In Simple Words: "Stateless" 🧠❌

> **Stateless** means the guard has **no memory**. He checks **every single person, every single time**, whether they're coming in *or* going out. He doesn't remember "oh, I let this person in earlier, so they can leave." Each direction is judged **separately** by its own rules.

Navigate: **VPC → Security → Network ACLs**

```
👀 You'll see a NACL already associated with the default VPC's subnets
   (three subnets in the demo's region)
```

### 📥 Inbound Rules of the Default NACL

| Rule # | Type | Action |
|---|---|---|
| **100** | All traffic | ✅ **Allow** |
| **\*** | All traffic | ❌ **Deny** |

### 🤔 What Does the `*` Rule Mean?

> The last rule (`*`) says "Deny everything." But if you click **Edit inbound rules**, you'll see it **isn't actually an editable rule**. It's just shown to tell you:
>
> **"If none of the numbered rules above make a decision, the default answer is DENY."**

> 🧒 It's the guard's **fallback instruction**: "If nobody on my list matches, don't let them in."

## 5️⃣ Demo: Blocking a Range of IPs 🚫

> 💡 **Use Case:** There's a certain range of IP addresses you want to **block completely** from reaching your subnet.

### 📝 Steps

```
1️⃣ Select the NACL → Edit inbound rules → Add rule
2️⃣ Rule number: 99          (lower than 100, so it's checked FIRST)
3️⃣ Type: All TCP
4️⃣ Source: 10.10.0.0/16     (the range to block)
5️⃣ Allow/Deny: DENY
6️⃣ Save
```

### ✅ Result

| Traffic From | Outcome |
|---|---|
| 🚫 `10.10.0.0/16` | **Denied** (rule 99 is checked first) |
| 🌍 Anywhere else | **Allowed** (rule 100 allows everything else) |

> 🔢 After saving, the rules are shown in order: **99 on top, 100 below**.

### 🧒 Why Use 99 (a Lower Number)?

> The guard reads his list **from the lowest number upward**, and stops at the **first rule that matches**. If we had used a number *higher* than 100, rule 100 ("allow everything") would match first and the block would **never be reached**. So the **deny rule must come before the allow rule**, which means a **lower number**.

> 💡 **Good habit:** In real projects, leave **gaps** between rule numbers (like 100, 200, 300). That way you can **insert new rules in between** later without renumbering everything.

### ⬆️ Outbound Rules

> The same idea works for **outbound** traffic. You can **block your subnet from reaching specific websites or IP addresses**. Outbound rules work exactly like inbound rules.

## 6️⃣ Security Group vs NACL ⚖️ (Exam Favourite!)

| Feature | 💂 Security Group | 🚧 NACL |
|---|---|---|
| 📍 **Works at** | **Resource level** (instance, database) | **Subnet level** |
| 🧠 **State** | **Stateful** (remembers connections) | **Stateless** (no memory) |
| ✅❌ **Rule types** | **Allow rules only** | **Allow AND Deny rules** |
| 🔢 **Rule order** | All rules evaluated together | Checked in **number order**, lowest first |
| 🆕 **New one by default** | Denies inbound, allows outbound | **Denies** inbound and outbound |
| 🏠 **Default one** | Same-group traffic allowed in; all outbound allowed | Allows **all** inbound and outbound |
| 🔗 **Attachment** | Many per resource | **One NACL per subnet** (every subnet must have one) |

> 🎯 **When to use a NACL?** When you want to **block** something at the subnet level, like a **specific IP range**, since security groups can't write deny rules.

---

## ❓ Extra Important Question: "Since a NACL is stateless, if it allows traffic IN, does the reply automatically go OUT?"

> 💡 **Answer:** **No.** This is the key difference from a security group. Because a NACL has **no memory**, the **reply traffic is treated as a brand-new request** going the other way, and it must be allowed by its **own rule**. For example, if you allow inbound web traffic on port 80, the response from your server goes **out** on a **random high-numbered port** (called an *ephemeral port*, roughly 1024–65535), so your **outbound rules must allow that range too**. If they don't, the connection will fail even though the inbound rule looks perfect. (This detail goes beyond what the lecture covers, but it's the most common NACL mistake.)
>
> 🧒 **In simple words:** With a security group, the guard remembers "you were let in, so you can leave." With a NACL, the guard forgets, so you need **separate permission for the way out**.

## 📋 Master Cheat Sheet

```
🚧 NACL = stateless firewall at the SUBNET level
🔗 Every subnet is associated with exactly one NACL
✅ DEFAULT NACL → allows ALL inbound and outbound
❌ NEW custom NACL → DENIES all inbound and outbound
🔢 Rules have numbers: LOWER number = HIGHER priority (checked first)
✅❌ Supports BOTH allow and deny rules
🚫 No rule matches → DENIED (the "*" rule)
⬆️⬇️ Inbound and outbound rules are separate and work the same way
🧠 Stateless: reply traffic needs its own rule
```

## ✅ Final Takeaways

```

🚫 If a NACL blocks traffic, it never reaches your resources
🔢 Lower rule number wins, so put DENY rules at a LOWER number than a broad ALLOW
🧠 Stateless = no memory → inbound AND outbound need matching rules
✅ Default NACL is wide open | ❌ A new custom NACL blocks everything
🎯 Use a NACL to block a specific IP range (security groups can't deny)
```
