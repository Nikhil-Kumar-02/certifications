## 1️⃣ Authorizers 🔐

> 💡 **Core Idea:** Before a REST API call is processed, you want to confirm it's coming from an **authorized user**.

### 🛠️ Two Ways to Define Authorization Logic

| Option | Detail |
|---|---|
| ⚡ **Lambda Function** | Write custom logic to validate the incoming request |
| 🔑 **AWS Cognito** | AWS's user management service — integrate API Gateway directly with Cognito for auth *(covered later in the course)* |

## 2️⃣ API Keys 🔑

> 💡 **Core Idea:** API Keys **identify** individual API clients — this is about **identification**, not authentication/authorization.

```
1️⃣ Create an API key
2️⃣ Generate the key value
3️⃣ Client includes this key with every request
```

---

## 3️⃣ Usage Plans (Throttling, Burst, Quota) 🎚️

> 💡 **Core Idea:** Usage Plans attach **limits** to API keys.

| Setting | What It Controls | Example |
|---|---|---|
| 🚦 **Throttling** | Max requests per second, sustained | 100 requests/sec → 5×60×100 requests over 5 minutes |
| 💥 **Burst** | Max requests allowed in a sudden spike | e.g., cap at 800–1000 to guard against traffic spikes or DoS-like bursts |
| 📊 **Quota** | Total requests allowed per month | e.g., 100,000 requests/month |

> 🎯 **Key Insight:** Burst limits specifically help distinguish a **legitimate traffic spike** from something like a **denial-of-service attack** — without a cap, 10,000 sudden requests could overwhelm your backend.

## 4️⃣ Client Certificates 📜

> 💡 **Core Idea:** How does your backend (Lambda, EC2, etc.) know a request is *really* coming from API Gateway and not somewhere else?

```
1️⃣ Generate a Client Certificate for API Gateway
2️⃣ Backend verifies the certificate on incoming requests
```

## 6️⃣ Post-Deployment Features 🛠️

| Feature | What It Does |
|---|---|
| ⚡ **Caching** | Cache responses for a configurable **TTL (Time To Live)** |
| 🎚️ **Stage-Level Throttling** | Set throttling limits per deployment stage |

## 7️⃣ Canary Deployments 🐤

> 💡 **Core Idea:** Rolling out a new API version? Don't switch everyone over at once — send just a **percentage** of traffic to the new version first.

```
🐤 Canary Deployment → e.g., 10-15% of requests go to the NEW version
🎯 Remaining 85-90% stay on the CURRENT stable version
```

> 🎯 **Key Insight:** This lets you catch problems with a new version **before** it affects all your users — a safer, gradual rollout strategy.

## ❓ Extra Important Question: "What's the practical difference between an API Key and an Authorizer — do I need both?"

> 💡 **Answer:** They solve different problems and are often used **together**. An **API Key** identifies *which client* is calling (useful for tracking usage, applying per-client throttling/quotas via Usage Plans) — but it's not meant to be a security boundary, since API keys are relatively easy to leak or share. An **Authorizer** (Lambda-based or Cognito-based) actually verifies *who the user is* and *whether they're allowed* to make the call — a real authentication/authorization layer. A typical production setup uses an Authorizer to secure the API AND an API Key + Usage Plan to track and rate-limit individual client applications — they're complementary, not redundant.
