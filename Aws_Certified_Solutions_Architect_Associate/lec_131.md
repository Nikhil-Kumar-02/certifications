## 🧒 Quick Refresher in Simple Words

> 💂 A **security group** is like a **guard standing at the door of each house** in the colony. The guard has a list of rules: "Let in people from *this* place, on *this* door (port)."
>
> - **Inbound rules** = who is allowed to **come in**
> - **Outbound rules** = where your house is allowed to **go out to**

---

## 1️⃣ Where to Find Security Groups 🔍

> 💡 Security groups can be opened from **both** the **EC2 console** and the **VPC console** (under **Security**). It's the **same** security group in both places, with the same details.

> 📝 The instructor notes the VPC-side access is a newer addition, so the console layout may change over time.

---

## 2️⃣ The Default Security Group 🏠

> 💡 **Core Idea:** When you create a new VPC, AWS **automatically creates a default security group** for it.

### 📋 What the Default Security Group Allows

| Direction | Rule |
|---|---|
| ⬆️ **Outbound** | ✅ **All** traffic allowed |
| ⬇️ **Inbound** | ✅ Allowed **only from resources that use the same security group**. Everything else is denied. |

> 🧒 **In simple words:** It's a **"family members only"** rule. Anyone wearing the **same family badge** (same security group) can walk in. Strangers can't.

### 🔒 What You Can and Can't Do

| Action | Allowed? |
|---|---|
| ✏️ Edit its inbound/outbound rules | ✅ Yes |
| 🗑️ **Delete** it | ❌ **No** |

### 🖥️ What If You Don't Pick a Security Group?

```
EC2 instance with no security group chosen → gets the VPC's DEFAULT security group
```

> 💡 In practice, we've been **creating our own** security groups and attaching them to instances, so we can control the traffic much more precisely.

---

## 3️⃣ Security Groups & Resources (Many-to-Many) 🔗

```
🔁 ONE resource    → can have MANY security groups
🔁 ONE security group → can be used by MANY resources
```

| Rule | Detail |
|---|---|
| 🌐 **Same VPC only** | This many-to-many relationship works for resources in the **same VPC** |
| 🔄 **Changeable** | You can **change** a resource's security groups at **any time** |

---

## 4️⃣ New Security Groups ✨

When you create a **brand-new** security group:

| Direction | Default |
|---|---|
| ⬇️ **Inbound** | ❌ **No rules** = **all inbound traffic is denied** |
| ⬆️ **Outbound** | ✅ **All outbound traffic is allowed** |

> 🧒 **In simple words:** A new guard starts with the instruction **"Let nobody in, but let everyone go out."** You then add rules to open specific doors.

> ✏️ You can add, edit, and delete rules freely.

---

## 5️⃣ Important Port Numbers 🔌

> 🧒 **What's a port?** An IP address is the **building address**. A **port** is the **door number** inside the building. Different services use different doors.

### 🌐 Common Access Ports

| Port | Used For |
|---|---|
| **22** | 🔑 **SSH** (log in to Linux) |
| **3389** | 🖥️ **RDP** (log in to Windows) |
| **80** | 🌍 **HTTP** (websites) |
| **443** | 🔒 **HTTPS** (secure websites) |

### 🗄️ Common Database Ports

| Port | Database |
|---|---|
| **1521** | Oracle |
| **3306** | MySQL / Aurora |
| **1433** | Microsoft SQL Server (MSSQL) |

> 📌 **Exam Tip:** You won't be asked "What is the port for X?" directly. But you should be able to **recognize** that a port number is probably for a database, or for SSH, and so on.

> 💡 *Bonus (not in this lecture):* **PostgreSQL** uses port **5432**.

## 6️⃣ Scenario Questions 🧠

### ❓ Scenario 1: Can the source or destination of a rule be **another security group**?

```
✅ YES
```

Instead of an IP address, you can say **"allow traffic from resources in Security Group X."**

### 🎓 Example: The Classic Web App Setup

| Resource | Security Group | Rule |
|---|---|---|
| 🖥️ **EC2 instance** | `ec2-sg` | (its own rules) |
| 🗄️ **Database** | `db-sg` | **Inbound:** allow port 3306 **from source `ec2-sg`** |

> 🎯 **Result:** The database accepts connections **only from the EC2 instances**. Nobody else can reach it.

> 🧒 **In simple words:** Instead of writing down every visitor's address, you tell the database's guard: **"Only let in people wearing the web-server badge."** If you add more web servers later, they get the badge too, and no rule changes are needed. 🏷️

---

### ❓ Scenario 2: A **new** security group is assigned to both a database and an EC2 instance. Can they talk to each other?

```
❌ NO
```

> 💡 **Why:** A new security group has **no inbound rules**, so it doesn't even allow traffic from **its own members**. To make them talk, you must **add an explicit rule** allowing traffic from the same security group.

---

### ❓ Scenario 3: The **unchanged default** security group is assigned to both a database and an EC2 instance. Can they talk to each other?

```
✅ YES
```

> 💡 **Why:** The default security group **already has a rule** allowing traffic from resources in the same security group.

### 🔁 Side-by-Side

| Security Group Type | Members Can Talk to Each Other? | Why |
|---|---|---|
| 🏠 **Default (unchanged)** | ✅ Yes | Has a built-in "allow from self" rule |
| ✨ **Newly created** | ❌ No | No inbound rules at all |

---

## ❓ Extra Important Question: "If a security group allows inbound traffic on port 80, do I also need an outbound rule so the response can go back?"

> 💡 **Answer:** **No.** Security groups are **stateful**. (This point isn't spelled out in this lecture, but it's a frequent exam fact.) "Stateful" means the security group **remembers** the connections it has allowed. If a request is allowed **in**, the **reply** is automatically allowed **out**, whatever the outbound rules say, and the same works in the other direction. 
>
> 🧒 **In simple words:** The guard remembers faces. If someone was let in, the guard also lets them **leave**, without needing a separate "exit permission."
>
> Another related fact: security groups only have **allow** rules. You **can't write a "deny" rule**. Anything not explicitly allowed is simply denied. (You'll meet a different tool, **Network ACLs**, later in the course that works differently.)

## 📋 Master Cheat Sheet

```
🔍 Security groups are visible from BOTH the EC2 and VPC consoles (same thing)
🏠 DEFAULT SG: allows all outbound + inbound only from the same SG | editable, NOT deletable
🖥️ No SG chosen on an EC2 instance → default SG is used
🔗 Many-to-many: one resource ↔ many SGs, one SG ↔ many resources (same VPC)
🔄 SGs on a resource can be changed at any time
✨ NEW SG: NO inbound rules (all denied) + all outbound allowed
🏷️ A rule's source/destination can be another security group
🔌 22=SSH | 3389=RDP | 80=HTTP | 443=HTTPS | 1521=Oracle | 3306=MySQL/Aurora | 1433=MSSQL
```

## ✅ Final Takeaways

```
🏠 Default SG = "family only" (same SG can talk) | New SG = "nobody in" (no inbound rules)
🗑️ You can edit the default SG but never delete it
🔗 Many-to-many between SGs and resources within a VPC
🏷️ Use "source = another security group" to lock a database to just your app servers
🧪 Two same-SG scenarios: default SG → YES, they talk | new SG → NO, they don't
🔌 Know your common ports well enough to recognize them
```
