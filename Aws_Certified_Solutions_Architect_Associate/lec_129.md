## 1️⃣ The Golden Rule 🏆

```
✅ ALWAYS prefer NAT Gateway over NAT Instance
```

### Why?

| Benefit | Meaning |
|---|---|
| 🛠️ **Less administration** | AWS manages it for you |
| 🛡️ **More availability** | Built-in resilience |
| 🚀 **Higher bandwidth** | Handles more traffic |
| 🔐 **No security groups to manage** | Just create it and add a route |

---

## 2️⃣ Key Facts About NAT Gateway 📌

| Fact | Detail |
|---|---|
| 🔢 **IP version** | **IPv4 only** |
| 🚪 **For IPv6** | Use an **Egress-Only Internet Gateway** instead |
| 🔗 **Depends on the Internet Gateway** | It sits in a public subnet, and that subnet's route to the Internet Gateway is how it reaches the internet |

> 📌 **Exam Tip:** If you see **IPv6** in a question about outbound-only access, the answer is **Egress-Only Internet Gateway**, not NAT Gateway.

> 🧒 **In simple words:** The NAT Gateway is the front desk, but the front desk still needs the **colony's main gate (Internet Gateway)** to send mail out. **No Internet Gateway = a useless NAT Gateway.**

---

## 3️⃣ Side-by-Side Comparison ⚖️

| Feature | ☁️ NAT Gateway | 🔧 NAT Instance |
|---|---|---|
| 👷 **Who manages it?** | **AWS** | **You** (it's an EC2 instance) |
| 🌍 **Where is it created?** | **Public subnet** | **Public subnet** |
| 🚪 **Uses the Internet Gateway?** | ✅ Yes | ✅ Yes |
| 🛡️ **Availability** | Highly available **within one AZ**. For more, create one in **multiple AZs** | **You** are responsible for availability |
| 🚀 **Bandwidth** | High (the course notes **up to 45 Gbps**) | Depends on the **EC2 instance type** you choose |
| 📌 **Public address** | **Elastic IP is mandatory** | **Public IP or Elastic IP** (either) |
| 🔓 **Release the Elastic IP?** | ❌ Not until the NAT Gateway is deleted | N/A |
| 🔐 **Security groups** | ❌ Not needed | ✅ You must configure inbound and outbound rules |
| ✅ **Disable source/destination check** | Not applicable | ✅ Required |
| 🏰 **Usable as a bastion server?** | ❌ **No** | ✅ **Yes** |

> 📝 **Note on bandwidth:** AWS has increased NAT Gateway limits over time, so the exact number in the docs today may be higher than the 45 Gbps quoted in the course. The key point stays the same: **NAT Gateway handles much more traffic than a typical NAT instance.**

### 🤔 Why Does Bandwidth Matter So Much?

> 🧒 NAT devices are **shared**. If you have **1,000 EC2 instances** in your private subnets, **all of them** send their internet traffic through the same NAT device. It's like 1,000 people using **one front desk**. If the desk is slow or small, everyone waits. That's why a bigger, automatically scaling NAT Gateway is the safer choice.

---

## 4️⃣ Two Trivia Items 🧩

### 🔁 "Disable Source/Destination Check" (NAT Instance Only)

> 🧒 **In simple words:** By default, an EC2 instance is **strict about mail**. It only accepts traffic addressed **to itself** or sent **from itself**. A NAT instance, however, **forwards other people's traffic** (from private instances to the internet). So you must **turn off this strictness** on the NAT instance, or it will reject the traffic it's supposed to forward.

```
NAT Instance → disable the source/destination check ✅ (required)
NAT Gateway  → nothing to configure
```

### 🏰 What Is a Bastion Server?

> 💡 Sometimes you need to **log in to instances in a private subnet** (for example, to SSH in and do some work). But private instances can't be reached from the internet. So how do you get in?

```
You → 🏰 Bastion server (in the PUBLIC subnet) → 🔒 Private instance
```

> 🧒 **In simple words:** A bastion server is a **guest house at the colony gate**. You first check in at the guest house (it's on the public street, so you can reach it). From there, you walk into the private streets. 🚶

| Device | Can It Be a Bastion? |
|---|---|
| 🔧 **NAT Instance** | ✅ Yes (it's a regular EC2 instance you control) |
| ☁️ **NAT Gateway** | ❌ No (it's a managed service; you can't log in to it) |

---

## ❓ Extra Important Question: "A NAT Gateway is 'highly available within one AZ.' What happens if that whole Availability Zone goes down?"

> 💡 **Answer:** The NAT Gateway in that AZ goes down with it. And if private subnets in **other AZs** were using that same NAT Gateway, they **lose their outbound internet access too**. The fix is the **Multi-AZ setup** mentioned in the lecture: create **one NAT Gateway in each AZ**, and point each AZ's private subnet route table to the NAT Gateway **in its own AZ**. That way, a failure in one AZ affects **only that AZ's** outbound traffic. It costs more (you pay for each gateway), so it's a trade-off between **cost** and **resilience**. This ties nicely to the "architect mindset" lenses from Lecture 87.

## 📋 Master Cheat Sheet

```
🏆 Prefer NAT GATEWAY over NAT INSTANCE (almost always)
🔢 NAT Gateway = IPv4 only | IPv6 → Egress-Only Internet Gateway
🌍 Both live in a PUBLIC subnet and rely on the INTERNET GATEWAY
📌 NAT Gateway → Elastic IP mandatory (can't be released until the gateway is deleted)
📌 NAT Instance → Public IP or Elastic IP
🔐 NAT Gateway → no security groups | NAT Instance → needs security groups
🔁 NAT Instance → must DISABLE source/destination check
🛡️ NAT Gateway → HA within one AZ; use MULTI-AZ for more
🚀 NAT Gateway → much higher bandwidth (instance bandwidth depends on instance type)
🏰 NAT Instance CAN be a bastion server | NAT Gateway CANNOT
```

---

## ✅ Final Takeaways

```
🏆 NAT Gateway = managed, available, high bandwidth, no security groups → the default choice
🔧 NAT Instance = DIY, flexible, but you manage everything (and it can double as a bastion)
🔢 NAT Gateway is IPv4 only; IPv6 uses an Egress-Only Internet Gateway
🌍 Both must sit in a PUBLIC subnet, because they need the Internet Gateway
🛡️ For higher availability, deploy NAT Gateways in multiple AZs
🏰 Only a NAT Instance can act as a bastion server
```
