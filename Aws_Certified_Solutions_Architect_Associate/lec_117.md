## 1️⃣ Revisiting `ec2-security-group` 🔐

Navigate: **EC2 → Security Groups → ec2-security-group**

> 💡 **Core Idea:** Security Groups have both **Inbound rules** (traffic coming in) and **Outbound rules** (traffic going out) — and CIDR blocks define exactly *which* IP addresses those rules apply to.

---

## 2️⃣ Example 1: Allowing HTTPS from a Range 🔒

```
📋 Rule: TCP, Port 443, Source: 172.31.0.0/16
```

> 🎯 **What This Means:** Allow **HTTPS traffic** (port 443) from any IP address within the `172.31.0.0/16` range — that's a range of **65,536 addresses** (recall: `32 - 16 = 16` variable bits → `2^16 = 65,536`).

---

## 3️⃣ Example 2: Allowing SSH from a Single IP 🔑

```
📋 Rule: TCP, Port 22, Source: <specific-ip>/32
```

> 🎯 **What This Means:** Allow **SSH traffic** (port 22) from **exactly one IP address** — since `/32` means all 32 bits are fixed, leaving zero variable bits (`2^0 = 1` address).

### 📌 Exam-Critical Reminder

```
🎯 /32 = EXACTLY ONE IP address
```

> 💡 **Real-World Use Case:** This is a common security pattern — restrict SSH access to only *your* current working IP address, so nobody else can SSH into that EC2 instance.

---

## 4️⃣ Example 3: Allowing Outbound to Everywhere 🌍

```
📋 Rule: Outbound, Destination: 0.0.0.0/0
```

> 🎯 **What This Means:** Allow outbound traffic to **every possible destination** — recall from Lecture 116 that `/0` means zero bits are fixed, so **all** IP addresses are covered.

> 📝 **Side Note:** You may also see an IPv6 equivalent CIDR format in some outbound rules — not something to worry deeply about at this stage.

---

## ❓ Extra Important Question: "If restricting SSH to a single /32 IP is best practice, what happens to my access if my home/office IP address changes (which is common with most home internet connections)?"

> 💡 **Answer:** You'd lose SSH access to that instance until you update the security group rule with your **new** IP address — this is a common real-world annoyance with dynamic IPs. Practical mitigations include: using a **VPN with a static IP** so your outbound IP never changes, connecting through a **bastion host / jump box** with a fixed, known IP that you separately secure, using **AWS Systems Manager Session Manager** (which doesn't require inbound SSH access at all — it connects via the SSM agent instead), or simply updating the security group's `/32` rule whenever your IP changes (tedious, but workable for infrequent access). For frequently changing IPs, Session Manager is often the most secure and convenient modern approach since it eliminates the need for an open SSH port entirely.

## 📋 Master Summary Table

| Rule Type | CIDR Used | What It Allows |
|---|---|---|
| 🔒 **Inbound HTTPS** | `172.31.0.0/16` | HTTPS (port 443) from a range of 65,536 addresses |
| 🔑 **Inbound SSH** | `<ip>/32` | SSH (port 22) from exactly ONE specific IP address |
| 🌍 **Outbound (all)** | `0.0.0.0/0` | Traffic to ANY destination — all IP addresses |

---

## ✅ Final Takeaways

```
🔐 Security Groups use CIDR blocks to define exactly WHICH IPs a rule applies to
🔒 /16 → a broad range (65,536 addresses) — used for HTTPS from a known network
🔑 /32 → exactly ONE IP address — used to lock down SSH to a single trusted source
🌍 0.0.0.0/0 → EVERY possible IP address — commonly used for open outbound rules
📌 EXAM TIP: /32 = one IP, /0 = all IPs — know this cold!
```
