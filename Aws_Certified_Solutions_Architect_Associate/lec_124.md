# 🎯 Lecture 124: Building a Test API to Check Internet Access (API Gateway + X-Ray)

> 📚 **Course:** AWS Certified Solutions Architect – Associate
> 🧩 **Section:** Virtual Private Cloud (VPC)
> ⏱️ **Type:** Hands-On Setup (⭐ A helper tool for the next few VPC lectures!)

---

## 🎯 What This Lecture Is About

> 🎬 Right now **both** our subnets are public, which isn't what we want. In the next lectures, we'll change the route tables to make one public and one private. But how will we **know** whether an instance can still reach the internet?

> 💡 **The Plan:** Build a tiny API that **records every call** made to it. If an instance can call our API, it has internet access. If the calls stop, it doesn't.

```
1️⃣ Why We Need This Test API
2️⃣ Create the API (REST + Mock)
3️⃣ Set a "Hello World" Response
4️⃣ Deploy It
5️⃣ Turn On X-Ray Tracing
6️⃣ See the Traces
```

---

## 🧒 The Idea in Simple Words

> 🔔 Think of the API as a **doorbell with a camera**. Every time someone presses the bell (calls the API), the camera (X-Ray) records who rang and when.
>
> If our EC2 instance can reach the internet, it can press the bell, and we'll see it in the recording. If it can't reach the internet, the bell never rings. We find out **without even logging in to the instance**.

> ✅ You don't need to understand API Gateway deeply to build this. (It's optional too, but it makes the next lectures much clearer.)

---

## 1️⃣ Create the API 🛠️

Navigate: **Services → API Gateway → Create API**

```
1️⃣ Choose: REST API → New API
2️⃣ Name: test-api
3️⃣ Keep the defaults → Create API
4️⃣ Actions → Create Method → choose GET → click the tick (✔)
5️⃣ Integration type: Mock → Save
```

> 🧒 **What is a "Mock" integration?** It means the API doesn't call any real backend (no Lambda, no server). It just sends back a **pre-set reply**. It's like a recorded voice message: no real person on the other end, but the caller still gets a response. Perfect for testing!

---

## 2️⃣ Set a "Hello World" Response 💬

Click **Test** at this point and you'll see an **empty response** (no data). Let's make it more useful:

```
1️⃣ Open "Integration Response"
2️⃣ Expand the response and click the application/json entry
3️⃣ In the template box, enter:
```

```json
{ "message": "Hello World" }
```

```
4️⃣ Save (click Save again if prompted)
5️⃣ Go back to the GET method → Test
```

### ✅ Result

```
{ "message": "Hello World" }
```

> 💡 **Tip:** The console screen can be a little fiddly here. If the response is still empty, make sure you clicked **Save** inside the template box.

---

## 3️⃣ Deploy the API 🚀

```
Actions → Deploy API → Stage: Dev → Deploy
```

> 🎯 **Key Insight:** Once deployed, the API gets a **public URL**. Open it in a browser and you'll see the "Hello World" message. This URL is what our EC2 instances will call.

---

## 4️⃣ Turn On X-Ray Tracing 🔍

```
1️⃣ Go to the Dev stage → Logs/Tracing
2️⃣ Enable X-Ray Tracing
3️⃣ Save Changes (takes about a minute)
```

> 🧒 **What is X-Ray?** It's AWS's tracing tool. It records the details of each request: when it came, how long it took, and **where it came from (the client IP)**. Think of it as the doorbell camera.

---

## 5️⃣ See the Traces 👀

```
1️⃣ Open Services → X-Ray
2️⃣ Call the API URL a few times from your browser
3️⃣ Refresh X-Ray → open Traces
```

| What We Did | What X-Ray Showed |
|---|---|
| Called the API 2 times | **2 traces** |
| Called it 3 more times | **5 traces** in total |

> 🎯 **The Payoff:** From now on, if any machine calls this URL, we'll see it in X-Ray, including its **client IP**.

---

## ❓ Extra Important Question: "Why not just log in to each EC2 instance and run a ping or curl to check the internet?"

> 💡 **Answer:** Because of **what we're about to do**. When we make a subnet private, we **lose the ability to log in to its instances from the internet**. We'd be locked out of the very machine we want to test! With this API, the instance does the calling by itself, and we watch the results from outside in X-Ray. It also gives us a **continuous record over time**, so we can see exactly *when* the connection stops or starts after each route table change. That's much more useful than a one-time manual check.
