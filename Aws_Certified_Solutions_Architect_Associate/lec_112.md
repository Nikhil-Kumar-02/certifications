## 1️⃣ Core Purpose 🚪

> 💡 **Core Idea:** API Gateway provides **API Lifecycle Management** for:

```
🌐 RESTful APIs
🔄 WebSocket APIs
```

> 🎯 **Key Insight:** You can run **multiple versions** of the same API simultaneously through API Gateway — essential as your API evolves over time.

---

## 2️⃣ Key Features 🛠️

| Feature | What It Does |
|---|---|
| 🎚️ **Rate Limiting** | Controls how many requests a consumer can make over time |
| 🚦 **Throttling** | Protects backend systems from being overwhelmed by request spikes |
| 🔑 **API Keys** | Fine-grained access permissions — especially useful for **third-party developers** consuming your API |

---

## 3️⃣ Authorization Options 🔐

> 💡 **Core Idea:** API Gateway supports **three** distinct ways to authorize incoming API requests.

| Option | Best For |
|---|---|
| 🔐 **IAM** | Authorizing **internal AWS users** making requests |
| 🔑 **Amazon Cognito** | Managing and authorizing **external application users** |
| ⚡ **Lambda Authorizer** | A **custom Lambda function** that implements your own authorization logic |

> 🎯 **Key Insight:** Choose based on *who* is calling your API:
```
🏢 Internal AWS users        → IAM
👥 Your app's end users       → Amazon Cognito
🎨 Fully custom auth logic     → Lambda Authorizer
```

---

## ❓ Extra Important Question: "How do I decide between IAM authorization and a Lambda Authorizer for an API that only internal teams will call?"

> 💡 **Answer:** If your callers are already AWS principals (IAM users, roles, or federated identities) within your own AWS environment, **IAM authorization** is usually the simpler and more secure choice — it leverages infrastructure you already have, with no extra code to write or maintain, and integrates cleanly with AWS's existing permission model (IAM policies). A **Lambda Authorizer** makes more sense when your authorization logic doesn't map cleanly to IAM — for example, if you need to validate a custom token format, check against an external identity system, or apply business-specific rules that go beyond "does this IAM principal have permission." For purely internal, AWS-native calling patterns, start with IAM before reaching for the added complexity of a custom Lambda Authorizer.
