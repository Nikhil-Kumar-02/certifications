## 2️⃣ Task Roles & Task Execution IAM Roles 🔐

> ⚠️ **These two are commonly confused — know the difference!**

| Role | Purpose |
|---|---|
| 🎭 **Task Role** | Optional — gives your **running application** permission to access AWS services (e.g., your container needs to talk to an RDS database) |
| 🔧 **Task Execution IAM Role** | Gives **ECS itself** permission to do setup work — like pulling the Docker image from a registry, or pushing container logs to **CloudWatch** |

> 🎯 **Key Insight:** Task Role = "what my *app* can do." Task Execution Role = "what *ECS* can do on my behalf to get things running."

---

## 3️⃣ Service & Cluster 🔧

| Concept | Definition |
|---|---|
| 🔧 **Service** | Runs and maintains a specified number of tasks — the **desired count** |
| 📦 **Cluster** | A grouping of one or more **container instances** (EC2 instances that run your tasks) |

> 💡 **Fargate Note:** With Fargate, you don't manage EC2 instances at all — no visibility into the underlying cluster hardware.

---

## 4️⃣ Container Instances & Container Agent 🖥️

```
📦 Container Instance = an EC2 instance that's part of your ECS cluster
🤖 Container Agent = software running on each EC2 instance, enabling it to communicate with the cluster
```

> 🎯 **Key Insight:** AWS provides **pre-built AMIs** with the container agent already installed, making it easy to add EC2 instances to a cluster.

### 💻 Launch Type Options (for EC2-based clusters)

```
💵 On-Demand instances
💸 Spot instances
```

## 5️⃣ Application Load Balancer Features for ECS ⚖️

| Feature | What It Does |
|---|---|
| 🔀 **Dynamic Host Port Mapping** | Allows multiple tasks from the **same service** to run on a single EC2 instance — the ALB load balances between them |
| 🛣️ **Path-Based Routing** | Routes requests to different microservices based on the URL path (e.g., `/microservice-a` vs `/microservice-b`) |

---

## ❓ Extra Important Question: "Why does ECS need a separate Task Execution Role AND a Task Role — why not just one permission set?"

> 💡 **Answer:** They operate at different layers and represent different security boundaries. The **Task Execution Role** is used by the **ECS infrastructure itself** *before* your application code even starts running — to pull the container image and set up logging. The **Task Role** is used by **your application code** *after* it's running, to make its own AWS API calls. Separating them follows the principle of least privilege: the infrastructure doesn't need (and shouldn't have) the same permissions your running application needs, and vice versa. If they were combined, a compromised application could potentially gain infrastructure-level permissions it has no business having (like modifying container registry access), which is a much broader attack surface than intended.

| Concept | Key Point |
|---|---|
| 🐳 **Container Definition** | Image, memory, CPU, ports |
| 🎭 **Task Role** | App-level AWS permissions (e.g., access RDS) |
