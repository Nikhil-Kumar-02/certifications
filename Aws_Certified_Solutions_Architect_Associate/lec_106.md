## 3️⃣ Understanding & Modifying the Code ✍️

The hardcoded response lives right in the function code:

```javascript

body: JSON.stringify('Hello from Lambda!')
```

> 🎓 **Demo Tweak:** Changed the message to `"My first Lambda function"`, saved, and re-tested — the new message appeared immediately. No redeployment ceremony needed.

## 4️⃣ Using console.log for Debugging 🪲

```javascript
console.log(event);
```

> 💡 **Core Idea:** The `event` object represents the incoming request data. Logging it lets you see exactly what data your test event (or a real request) sent in — e.g., `key1: 'value1', key2: 'value2'`.

> 🎓 You can edit the **test event's** JSON data (Configure test events) to simulate different inputs and see how your function responds and logs.

## 5️⃣ Working with Environment Variables 🔧

> 💡 **Why Use Them?** You might connect to a different database in dev vs. QA vs. production. Environment variables let you configure that without hardcoding values into your function.

### 🎓 Demo Steps

```
1️⃣ Add environment variable: ENVIRONMENT = DEV
2️⃣ Access it in code: process.env.ENVIRONMENT
```

### 🌟 Built-In Environment Variables (Node.js examples)

| Variable | What It Gives You |
|---|---|
| `process.env.AWS_REGION` | The AWS region the function runs in |
| Execution environment | Which runtime (e.g., `nodejs12.x`) |
| Function name | The Lambda's name |
| Function memory size | Configured memory |
| Function version | Current version being executed |

> 🔗 **Other Languages:** In Java, the equivalent is `System.getenv("AWS_REGION")`.

> 🎓 **Final Demo Output:** After combining a custom environment variable with a built-in one, the function returned: `"My first lambda function from DEV"` — proving environment-specific configuration works seamlessly.

## ❓ Extra Important Question: "If I can edit and save Lambda code directly in the console, is that a good practice for real projects?"

> 💡 **Answer:** It's great for learning and quick experimentation (like this demo), but **not recommended for production workloads**. In real projects, you'd typically manage Lambda code through a proper CI/CD pipeline — writing code in a repository, running tests, and deploying via tools like AWS SAM, the Serverless Framework, or infrastructure-as-code (CloudFormation/Terraform). This gives you version control, rollback capability, and consistency across environments — things the inline console editor doesn't provide. The console editor is best reserved for prototyping, debugging, or truly tiny functions.
