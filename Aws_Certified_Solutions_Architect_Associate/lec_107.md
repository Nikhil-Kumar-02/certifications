## 1️⃣ Monitoring with CloudWatch 📊

Under the **Monitoring** tab, CloudWatch automatically tracks:

```
🔢 Number of invocations
⏱️ Duration of each request
✅ Success count
🚦 Throttled requests
❌ Delivery failures
🔀 Concurrent executions
```

> 🎯 **Key Insight:** For each invocation, you can drill into the exact **log stream** in CloudWatch Logs — and the console even highlights the **most expensive invocations** in your selected time period.

## 2️⃣ Tracing with AWS X-Ray 🔍

> 💡 **Core Idea:** X-Ray is AWS's go-to tool for **tracing requests** — including calls between Lambda functions.

### 🎓 Enabling X-Ray Tracing

```
1️⃣ Go to Configuration → scroll to AWS X-Ray
2️⃣ Enable the tracing checkbox
3️⃣ Save (Lambda automatically grants the needed permissions!)
```

### 📈 What You See in X-Ray

```
🗺️ A trace map: Client → API Gateway/Lambda → Function execution
⏱️ Time breakdown per step (e.g., 25ms spent processing)
✅ Success count and average response time across all traced requests
```

> 🎯 **Key Insight:** If a request flows across **multiple Lambda functions**, X-Ray traces the entire chain — invaluable for debugging distributed serverless architectures.

## 3️⃣ Memory & CPU Relationship 💾⚙️

> 💡 **Core Idea:** In Lambda, **CPU allocation is proportional to memory allocation** — you can't set CPU directly.

```
🔼 More memory → More CPU
🔽 Less memory → Less CPU
```

| Setting | Value |
|---|---|
| 🔽 **Default Memory** | 128 MB |
| 🔼 **Maximum Memory** | 3008 MB |

> 💰 **Cost Note:** Price per invocation is **directly proportional** to memory allocated. **Best Practice:** Allocate the *minimum* memory your function actually needs — don't over-provision.

---

## 4️⃣ Timeout Settings ⏱️

| Setting | Value |
|---|---|
| 🔽 **Default Timeout** | 3 seconds |
| 🔼 **Maximum Timeout** | 15 minutes (900 seconds) |

> ⚠️ **Important:** If your function doesn't finish within the configured timeout, execution is **terminated**. For anything needing hours to run (like a big batch job), you **can't** just extend Lambda's timeout indefinitely — you need to break the work into multiple Lambda invocations instead.

> 📌 **Exam Tip:** Remember **900 seconds = 15 minutes** as the hard ceiling (this limit has increased over time — it used to be 5 minutes).

## 6️⃣ VPC, Concurrency & Async Invocations 🌐

### 🔒 VPC (Virtual Private Cloud)

```
Default: Lambda runs in a PUBLIC network
Optional: Run Lambda inside a PRIVATE network (VPC)
```

### 🔀 Concurrency

| Setting | Detail |
|---|---|
| 🔢 **Default Concurrent Invocations** | 1,000 |
| ⚠️ **Sudden Spike Behavior** | If invocations jump quickly (e.g., 100 → 500), some requests may experience **latency fluctuation** while Lambda scales up |
| 💰 **Provisioned Concurrency** | Pre-warms capacity for consistent latency — but costs **more** |

### ⚡ Asynchronous Invocations

> 💡 When Lambda processes requests from a **queue**, that's an asynchronous invocation.

```
🔁 Failed request → RETRY (up to a configured max attempts)
☠️ Still failing after max retries → sent to a DEAD-LETTER QUEUE (DLQ)
```

> 🎯 **Key Insight:** The dead-letter queue means you never silently lose failed events — you can inspect and reprocess them later, improving overall **reliability**.

---

## ❓ Extra Important Question: "If more memory always means more CPU, why wouldn't I just max out memory to make my function run faster?"

> 💡 **Answer:** Because cost scales directly with memory allocation, and for many functions, the extra CPU doesn't actually translate into meaningfully faster execution — especially for I/O-bound functions (like ones mostly waiting on a database or API call) rather than CPU-bound ones (like heavy computation or data processing). The best practice is to actually **test different memory settings** for your specific function and measure the trade-off between execution duration and cost — sometimes a higher memory setting reduces duration enough to actually lower your total cost (since you're billed on duration × memory), but this isn't guaranteed and needs to be verified per function rather than assumed.
