# 🎯 Lecture 126: Making One Subnet Truly Public and the Other Truly Private

> 📚 **Course:** AWS Certified Solutions Architect – Associate
> 🧩 **Section:** Virtual Private Cloud (VPC)
> ⏱️ **Type:** Hands-On Demo (⭐ Fixes the problem we found in Lecture 122!)

---

## 🎯 What This Lecture Is About

> 🎬 Quick status check: we have a VPC, two subnets, and a route table that sends internet traffic through the Internet Gateway. Both instances can be pinged, reached with Instance Connect, and both show up in X-Ray. **That's not what we want.** The private instance should *not* be reachable from the internet.

```
1️⃣ Where We Are Now
2️⃣ Create a Separate Route Table for the Public Subnet
3️⃣ Add the Internet Route to It
4️⃣ Link It to the Public Subnet
5️⃣ Remove the Internet Route from the Shared Table
6️⃣ Verify the Result
7️⃣ The Official Definition
```

---

## 🧒 The Plan in Simple Words

> 🏘️ **Colony analogy again:** Right now, **one signboard** ("take the main gate to go outside") is shared by **both streets**. We want a signboard **only for the public street**.
>
> So we will:
> 1. 🪧 Make a **new signboard** just for the public street, pointing to the main gate.
> 2. 🔗 Put it up **only on the public street**.
> 3. 🗑️ **Remove** the "main gate" instruction from the shared signboard, so the private street no longer knows the way out.

---

## 1️⃣ Where We Are Now 📍

| Resource | Route Table Used | Has Internet Route? |
|---|---|---|
| 🌍 `my-public-subnet` | My VPC Route Table (shared) | ✅ Yes |
| 🔒 `my-private-subnet` | My VPC Route Table (shared) | ✅ Yes ← **the problem!** |

> 💡 **Why they share:** When you create a subnet, it uses the **VPC's own route table** by default. That's an "implicit" association, so we never chose it ourselves.

---

## 2️⃣ Create a Separate Route Table for the Public Subnet 📋

Navigate: **VPC → Route Tables → Create route table**

```
📛 Name: My Public Subnet Route Table
🌐 VPC: my-custom-vpc
```

### 👀 What's Inside a New Route Table?

```
Only ONE route: the local route (VPC's CIDR → local)
```

> 💡 A brand-new route table only allows **local traffic** inside the VPC. We'll add the internet route ourselves.

> ⚠️ **Console Tip:** After creating it, the screen may show **My VPC Route Table** selected by mistake. Make sure you select **My Public Subnet Route Table** before editing.

---

## 3️⃣ Add the Internet Route to It 🪧

```
1️⃣ Select My Public Subnet Route Table → Routes → Edit routes
2️⃣ Add route → Destination: 0.0.0.0/0
3️⃣ Target: Internet Gateway → my-internet-gateway
4️⃣ Save routes
```

---

## 4️⃣ Link It to the Public Subnet 🔗

> 🎯 **Key Idea:** A subnet can say, **"I don't want to share the VPC's route table. I want my own."** That's called a **route table association**.

```
1️⃣ Go to Subnets → select my-public-subnet
2️⃣ Route table tab → Edit route table association
3️⃣ Choose: My Public Subnet Route Table
4️⃣ Save
```

### ✅ Now

| Subnet | Route Table Used |
|---|---|
| 🌍 `my-public-subnet` | **My Public Subnet Route Table** (its own) |
| 🔒 `my-private-subnet` | My VPC Route Table (still shared) |

> ⚠️ **But both tables still have the internet route**, so X-Ray still shows requests from both instances. One more step!

---

## 5️⃣ Remove the Internet Route from the Shared Table 🗑️

```
1️⃣ Go to My VPC Route Table → Edit routes
2️⃣ Delete the 0.0.0.0/0 → Internet Gateway route
3️⃣ Save routes
```

> 📝 **Note on names:** The instructor says "Default VPC Route Table" at one point, but the table being edited is the **custom VPC's table** (**My VPC Route Table**), the one the private subnet uses. Don't touch the default VPC's table.

### 🎯 Why Is This a Good Design?

> Any **new subnet** you create later will automatically use this shared table. Since it has **no internet route**, new subnets are **private by default**. Public access is something you grant **on purpose**, not by accident. 🔒

---

## 6️⃣ Verify the Result ✅

### 🔒 The Private Subnet

```
Route table: only the local route
Internet route: ❌ None
```

### 🌍 The Public Subnet

```
Route table: local route + 0.0.0.0/0 → Internet Gateway
```

### 🧪 Test Results

| Test | Public Instance | Private Instance |
|---|---|---|
| 💻 **Instance Connect** from the internet | ✅ Works | ❌ **Fails** |
| 👀 **New X-Ray traces** | ✅ Keep arriving | ❌ **Stop** (after a few minutes) |

> ⏱️ **Patience tip:** Wait 3–4 minutes and refresh X-Ray. You'll see requests **only from the public subnet's instance**.

> 🤔 **Notice:** The private instance **still has a public IP**, yet it's unreachable. This proves the lesson from Lecture 120: **a public IP is useless without a route to the Internet Gateway.**

---

## 7️⃣ The Official Definition 📖

> 📌 **Exam-ready definitions:**

```
🌍 PUBLIC SUBNET  = a subnet whose route table has a route to an Internet Gateway
🔒 PRIVATE SUBNET = a subnet whose route table has NO route to an Internet Gateway
```

> 🎯 **Key Insight:** Until now we only *called* them public and private (just names). Now they genuinely **behave** that way. **The route table decides, not the name.**

---

## ❓ Extra Important Question: "The private instance can't be reached from the internet now. But it also can't reach OUT to the internet. What if it needs to download updates?"

> 💡 **Answer:** Great question. That's exactly the next problem. A truly private instance has **no path in or out**. Many private resources (like a database server) **never** need to be reached from the internet, but they **do** need to reach out, for example to download security patches. We want **outbound-only** access: "you can call out, but nobody can call in." The solution is a **NAT device**, which is our next topic.

## ✅ Final Takeaways

```
📋 By default, subnets share the VPC's route table
🪧 Make a SEPARATE route table for public subnets and link it to them
🗑️ Keep the shared (default) route table WITHOUT an internet route → private by default
🌍 Public subnet = has a route to an Internet Gateway
🔒 Private subnet = has NO route to an Internet Gateway
⚠️ A public IP alone does NOT make an instance reachable. The ROUTE does.
```
